Local proof does not complete a requirement, plan, phase or milestone. Use the existing `verify:email-delivery` command; no release wrapper is required. `local-preflight --channels email,sms,web-push --target local` uses the same config, expectations and artifacts flags and hash rules as email, with `--expect-switch false`. It loads no credentials and performs no network or command I/O. Inputs must inventory actual generated bytes including the preserved 0000 and generated 0001→0002 forward candidate. Keep the exact source SHA, dirty-diff digest, build profile, module/asset/migration aggregates, config digest and individual SQL hashes in the review record. A changed candidate invalidates approval.

After separate authorization, the existing CLI's `readiness --channels email,sms,web-push --target production --expect-switch true --approve-readiness --evidence <private-observations.json>` can **review operator observations offline** against those bytes. All other input flags remain mandatory. The private observations file uses the runtime configuration names (`notificationExpectedTargetIdentity`, `notificationExpectedDeploymentId`, `notificationExpectedBundleHash`, `notificationExpectedMigrationHash`, `notificationExpectedConfigHash`), root/provider/VAPID material and `notificationEmailEvidence`, `notificationSmsEvidence`, `notificationWebPushEvidence` JSON strings. Never commit or log that file. Both `notificationSmsEnabled` and `notificationWebPushEnabled` must be true. This review uses the exact runtime-safe evidence contract, channel key-material digests, declared browser gates and maximum 24-hour validity. It cannot renew the oldest evidence expiry.

The result is still `local-candidate`: `channelReadiness` describes accepted supplied observations, not a new inspection of production or a device receipt. Live gates in the output remain pending. No observation is installed, switch changed or provider called. Missing, stale, future, asymmetric, target/hash/key drift and incomplete evidence fail with fixed output. Use independently authenticated observations; the local reviewer cannot establish their provenance. Existing email modes retain their interface and authentication requirements.

All errors are sanitized and all attempts are bounded; neither synthetic acceptance nor this output can be installed as runtime production evidence.

## SMS evidence

SMS uses an independent private `NUXT_BREVO_SMS_SENDER` (1–11 ASCII alphanumerics or 1–15 digits), with no fallback to the email display name. Email keeps `NUXT_BREVO_SENDER_NAME`. SMS readiness evidence binds the root, API key and SMS sender; changing the SMS sender invalidates that evidence without changing the email identity.

### Transactional SMS webhook

Brevo requires a separate SMS webhook: `POST /api/notifications/brevo-events-sms`. Email continues to use `/api/notifications/brevo-events`. Configure both with `Authorization: Bearer <NUXT_BREVO_CALLBACK_SECRET>`; never put the secret in the URL. Both routes authenticate before body consumption and share the 64 KiB/50-event bounds.

The SMS route accepts the documented transactional `msg_status`, `messageId`, numeric webhook `id` and numeric UTC `ts_event` fields. Delivered, soft/hard bounce, rejected and unsubscribed events correlate only to one existing submitted SMS event delivery with the same stored provider message ID. Phone numbers, tags and references are not identity authority. Retries are idempotent; terminal states cannot be downgraded. Hard bounce/unsubscribe suppress only the matching SMS destination and invalidate that generation's pending work. Subscribe never reactivates a contact. Unsupported/unmatched payloads are acknowledged without mutation.

Lifecycle SMS provider IDs are not retained by the current outbox schema, so these callbacks do not track first/recovery messages. No schema migration or synthetic receipt is introduced. The endpoint alone does not establish live provider interoperability or set `notificationSmsDeliveryCallbacksConfigured`/`deliveryCallbackAuth` evidence; verify the actual account webhook authentication and a separately authorized real event receipt before declaring those gates passed. Contract reference: https://developers.brevo.com/docs/transactional-webhooks#transactional-sms .

- Authenticate the real account, transactional sender, sufficient credits/cost, recipient-country support, Czech/EU compliance and classification. Review GSM-7/one-segment behavior and cost before using dedicated controlled recipients.
- Observe first signup and requested recovery messages carrying the token-scoped management link. Observe a relevant event receipt, then explicit shared management POST stop. Confirm SMS contact removal, keyed SMS suppression, all nonterminal payload invalidation/scrubbing and **no second message after stop**, including already-queued work. One bearer controls one channel.
- Shared management stop is authoritative; a provider-specific opt-out callback is not a prerequisite. No inspected account-specific authoritative SMS callback contract is established. Report delivery callback evidence as **not-configured** when absent; never fabricate opt-out success or call an unknown callback endpoint. If a supported authoritative delivery callback is configured, separately verify its exact authentication, correlation and replay behavior; runtime evidence then requires `deliveryCallbackAuth: passed`. This optional SMS contract cannot downgrade email's mandatory authenticated callback gate.
- HTTP acceptance, a synthetic receipt or a provider message ID alone does not prove handset delivery. Submit each controlled message once through existing production lifecycle/Queue boundaries. On timeout or ambiguous acceptance, inspect authorized durable/provider state; do not blindly resend.

## Native push evidence

- Use externally provisioned dedicated VAPID material. Replacement changes application-server identity and requires an explicit re-subscription policy; old device subscriptions cannot be assumed compatible. Root replacement also has the cryptographic limitations in email operations.
- Verify HTTPS, service-worker scope/registration, explicit permission gesture and subscriptions on every claimed family: Chrome/Edge, Firefox, Safari macOS, installed iOS/iPadOS Home Screen where supported. Record exact browser/device/OS versions, install state and permission outcome. Desktop-mode iPad capability must not be rejected solely by UA.
- Observe visible notification/fallback, click destination, first message, event receipt, current-device recovery, stop and 404/410 stale-device retirement. Device receipt and no further send after stop remain separate from RFC encryption/JWT unit proofs and browser doubles.
- Record each claimed family in `interoperability` and its `browser:<family>` gate; the runtime validator accepts `chromium`, `firefox`, `safari-macos`, `ios-home-screen`. Do not claim untested families.

## Smoke, privacy, expiry and incidents

Immediately after an authorized joint release verify all-false/true readiness expectations, controlled SMS/push first/recovery/event flows, scoped stop and no-second-send, Queue/DLQ/retry health, cron and PII-safe persistent logs. Do not publish destinations, endpoint URLs, auth keys, provider IDs, bearer links, callback bodies or secret material in evidence, logs, analytics or Queue messages. Queue pointers are not delivery authority; final D1 state remains authoritative.

Runtime observations are bounded to 24 hours and exact target/deployment/config/bundle/migration/key identities. Retain private evidence under the operator-owned incident/review record with bounded expiry and retention; do not renew by copying timestamps. Expiry, identity changes or missing gates fail closed.

On any smoke failure or uncertain privacy/delivery authority, immediately jointly disable SMS/push through the reviewed existing Worker configuration/deploy workflow. Inspect durable state and Queue/DLQ before resuming; do not clear suppression, replay ambiguous sends or treat a failed CLI as success. Email manual disablement is independent when email is affected. Record the incident and rollback target/SHA/config; fresh evidence and renewed explicit approval are required before re-enablement. There is no automatic rollback or secret-install wrapper.
